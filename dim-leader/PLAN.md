## 3. 本次分析新增发现（N*）

> N 为本次复查新发现；原 I/F/R 编号全部保留，状态就地更新。

- **N1 `eval-place` 未走网格（P1，0.5h）**：`avoid-leader=1` 时 :786 走 `eval-place`，其内部 :211 仍对 `placed` 全表线性扫（含 obstacles，5000+ 项）。网格已建好却没接上，`avoid=1` 仍是 O(n³)。
- **N2 走廊后处理是新的性能瓶颈（P1，0.5h）**：:852-866 每个标签试 5 条走廊 × `route-cross` 全量扫 `boxes`。500 标签 ≈ 3.75M 次 `seg-rect-hit`（每次含 2 次 `pt-in-rect` + 4 次 `seg-seg-hit`）≈ 2200 万次浮点比较。网格修完后这一段就是新的主瓶颈。
- **N3 全局变量在函数体中间裸 setq（P0，0.1h）**：:593-594 的 `(setq dim-leader:*chip-error* nil)` / `(setq dim-leader:*unplaced* nil)` 顶格插在 `layout-chip` 函数体里、缩进也丢了；应进 `/` 私有表或只在 `run` 里重置一次。
- **N4 `free` 未进私有变量表（P1，0.1h）**：:796/:807 在 `dim-leader:layout` 里 setq `free` 但 `/` 表里没有它 → 泄漏为全局（lint 2 条）。每轮 k 都重置为 nil，功能上侥幸正确，仍是全局污染。
- **N5 `make-grid` 里 `g` / `row` 未进私有表（P1，0.1h）**：:115-123（lint 4 条）。
- **N6 契约描述过期**：见 2.1。
- **N7 布局 5/7/8 不避让既有文字（P1，2h）**：见 2.2。要么接上障碍校验，要么在 README 明确"这三种布局不避让图上文字"并订正表述。
- **N8 `ssget` 无 `ssset` 释放（P1，0.1h）**：3 处 `ssget "_X"`（:651/:686/:1327）无对应 `ssset`（lint 信息级）。反复跑 `run` 会累积选择集。
- **N9 配置无取值校验（P1，0.3h）**：`gap` 传 0/负数 → `rowPitch`/`levelH` 变 0 → `fix(/ x 0)` 抛错（:754/:903/:943）。`columns`/`zones` 传 0、`leader-colors` 传非法串同样无保护。
- **N10 版本与描述未跟功能走（P2，0.3h）**：`pkg.lsp` 仍 `0.0.1`，`:DESCRIPTION` 只提"自动分层"，未提 9 种布局 / 16 项配置 / 通道布线零共线重叠。
- **N13 窄带里堆行必然交叉 —— 要根治得换布局范式（P1，待评估）**：N12 把交叉从 13700 压到 779（N17 订正后的口径），但剩下的 779 是结构性的：一条带宽 W、点 m、行距 p 时，单行最多放 `W/p` 个标签，剩下必须堆 `m·p/W` 行；第 r 行的引线要越过外层 0..r-1 行的泳道，交叉数约 `Σ_r (m/cap)·r`。本图竖臂 46×176 装 256 个标签 → 6 行，这个代价下界与"标签数/带宽"成正比。**可选路子**：(a) 对窄带允许**文字沿圆心局部主方向排布**（不强制带方向），代价是失去正交保证；(b) 把 `lane-gap` 调大、给深层行单独开更外侧的泳道走廊，让穿越发生在空白走廊而非泳道密集区；(c) 接受现状并在文档里给出"交叉数 ≈ f(标签数/带宽)"的经验式，让用户按点密度选布局。三者都需先量化再决定，**不建议现在做**。
- **N14 `dim-leader:grid-add` 漏插桶 —— 布局 0/4 全面失效（P0，已修）**：未提交的网格索引（I6/R4）里，`grid-add` 的**不越界分支只把新盒 append 到 `all` 扁平表，从未调用 `grid-put` 塞进桶**（`dim-leader.lsp:144`）。后果是 `box-hit-grid` 永远查不到已放置的盒 → 恒判"空位" → 每个标签都选中第一个候选（原始位置）→ 引线退化成 2.00 单位的短 stub、507 个标签几乎全压在一起。507 点实测：布局 0 盒重叠 **2675**、布局 4 **2637**（README 旧记载布局 0 约 203，即明显劣化）。**已修**为 `(dim-leader:lst-set (dim-leader:grid-put g b) 7 (cons b (nth 7 g)))`；修复后布局 0 盒重叠 **2675→39**、布局 4 **2637→0**，平均引线 2.3→51.7 / 2.0→44.0。
  - **两个教训**：(1) Python 镜像的 `grid_add` 里**有** `rows[j][i].append(b)`，即这次是 **LISP 错、Python 对** —— 与 N11 方向相反，说明"照抄镜像"和"跑一遍所有布局"都不可省；(2) 我上一轮只验了布局 8（不走网格路径）所以完全漏掉，**逐布局回归必须在合入前跑完**，这正是路线图"阶段 0 不做不能往下走"的现实例证。
- **N15 布局 3 二维分区有 370 处文字盒重叠（P1，0.5h 排查）**：507 点实测唯一一个盒重叠不为 0 的可用布局（0/1/2/4/5/7/8 全为 0）。疑因与 N14 同源 —— `layout-zone2d`(:991) 的空白矩形搜索只按 `obstacles` 初始化栅格，**没有把已放置的标签回填**，后放的标签可以压住先放的。**待验证**：若每放一个就把它回填进栅格（或直接查 `placed`），370 应能压到接近 0。建议与 N14 一起回归。
- **N16 布局 6 应从菜单摘掉或加显式确认（P1，0.3h）**：实测 5 个点即跑不完并阻塞 CAD 十余分钟（§7.4）。它挂在菜单第 6 项，意味着用户一次误点就要等 CAD 假死。建议 `menu-items` 排除 6，或在 `run-layout` 里对 6 加 `(initget "布局6极慢，确认继续?")`。**这是可用性问题，优先级高于其代码质量。**
- **N17 引线交叉数的度量本身有 bug，所有历史数据虚高 2~5 倍（已修）**：原计数函数只把"同向共线"判掉，**其余情况一律 return True**，于是**两条 y 不同的水平引线段（永不相交）被误计为交叉**。507 点实测对比：布局 7 被虚报成 14432（实为 2959，5 倍）、布局 3 虚报 48771（实为 21955）、布局 1 虚报 45259（实为 35899）。正确口径是"**一横一竖相交**才算，T 形相接算，共线重叠与平行都不算"。
  - **结论未变**：布局 8 仍是最优，且改进幅度比原先报的更大（旧默认 13700 → 新默认 779，**−94%**，原报 −93%）。排序也微调：正确的是 L8 779 < L0 2395 < L4 2675 < L7 2959 < L2 4257 < L3 21955 < L5 25408 < L1 35899 —— **布局 7 实为第三好（2959）而非最差**，原先被虚高数据误导。
  - 已在新工具 `verify_layouts.py` 里改正，并加 `_selftest()` 锁住 8 个语义用例（X 形/T 形/平行/共线/端点相接），改动度量代码后必须先跑它。
- **N11 Python 镜像的 `ch_isotonic`(PAVA) 有 bug —— LISP 版一直是对的（已修）**：`layouts_py.py` 先 `blocks = [[x,1] for x in v]` 建好全部块，再 `for x in v:` 回头扫，合并只发生在**末尾两块**，中间的违例永远发现不了 → 输出间距可小到 0.003（pitch=4），标签互相压字。LISP 版（`channels.lsp:219-225`）是"逐个 append 并向左连级合并"，正确。**后果**：此前所有用 Python 镜像做的布局 8 质量分析（引线交叉数、盒重叠数）都是在测一个 LISP 根本不会产生的算法，据此得出的结论不可用。已按 LISP 修正镜像（`layouts_py.py:1080`）。**教训：镜像必须双向核对，不能只照抄 LISP 表面结构。**
- **N12 布局 8「零共线重叠」被当成了「不交叉」（P0，1.2h，已修）**：文档与 PLAN 一直只报"共线重叠 0 / 穿越文字盒 263→38"，从未报**引线交叉**数。实测 507 点：改前交叉 **13700** 处。根因是 `ch-band-v`/`ch-band-h` 把 PAVA 结果夹到**整条带**的 `minY/maxY`（`ch-band-v` 原来如此，`ch-band-h` 原来根本不夹），而一行 44 个点的 PAVA 最小跨度是 172、该行自身只跨 39，于是这行标签被摊到全带 176 单位上，引线要纵穿 130+ 单位、横切其余各行泳道。改为夹到**本行自己的**点范围后（整体平移，不破坏保序与最小行距）：交叉 **13700→779（−94%）**、穿文字盒 **497→19（−96%）**、盒重叠仍 **0**、耗时 20→12 ms、平均引线 224.8→221.6。`channels-blocks` 默认随之由 10 改为 0（分块路径被完全支配）。

### 7.5 CAD 环境注意事项（本次踩到的坑）

- 这台 CAD 的 `entget` 把 LWPOLYLINE 的组码 10 返回成**重复的 `(10 x y)`**（不是嵌套表），`(cdr (assoc 10 d))` 只能取到第一个顶点。要拿全部顶点必须遍历整个 entget 收集所有组码 10。`verify_dwg.py` 走 ezdxf 不受影响。
- 组码 50 在本 CAD 以**弧度**计（`place-text` 按此写入，90° 写 `pi/2`）。
- `open_dwg` 会重置 LISP 环境，重新 `load` 包源码后才能继续用。
- 长任务会触发 `cad.stallTimeout`（≈30 s）并进入冷却，之后连 `(getvar "DWGNAME")` 都会失败；冷却结束还会出现 `Worker reset`。**布局 6 这类不受控任务不要在生产图上试。**

## 10. 风险与开放问题

## 11. 附录：布局 6/7/8 设计要点与已否掉的方案

> 从旧版 PLAN 保留。这部分是**试错结论**，避免后来者重走；改布局前先读。

### 11.1 布局 6（芯片式左右分区）

- 按圆心 X 均值分左右两组；各自按 Y 升序，按纵向可容纳行数 `rowCap` 分列，列距 `maxw+gap`、行距 `maxh+gap`。
- 右侧文本左对齐(hj=0)、锚点 `edge+col*colPitch`；左侧右对齐(hj=2)、锚点 `edge-col*colPitch`；垂直居中(vj=2)。文字盒整体位于全部圆心/障碍之外，天然不压图元。
- 引线：正交通道搜索，候选通道来自 文本盒边缘/圆心/终点 展开的 x、y 值 + 上下轨道；代价 = 路径长度 + 折弯惩罚；已布引线按 `clearance` 膨胀为 keepout 递增避让。
- 硬校验：`routes-valid-p` 复核 引线×文字盒、引线×引线 均不相交；任一失败则整批不落图，错误写入 `dim-leader:*chip-error*`。
- **代价**：约 n^1.7。4 个点 2.2 s（LISP）/ 6.3 s（Python），16 个点 188 s，507 点外推约 14 小时。**大图不可用**，README 已标为"仅小图"。

### 11.2 布局 7（紧凑双侧，chip.lsp）

- 圆心按 X 对半分配左右（数量接近）；每侧按 Y 中位数分上/下两组，文字带绕点群中心 Y 居中。
- 文字独占行、K 列交错；行距=字高+gap、列距=字宽+gap；3 段正交引线 `圆心 →(横) lane →(竖) ty →(横) 文字内缘`。
- 每条引线独占 lane（lane 按序分配），故引线共线重叠极少；`dim-leader:side-distance` 控制走廊宽度。
- 引线颜色循环：`dim-leader:leader-colors`（ACI 空格分隔），`run` 对生成的 LWPOLYLINE 逐个 `entmod 62`。
- Python 参考：`chip_layout.py`（`--optimize` 做 Y 向折线降交叉）。

### 11.3 布局 8（通道布线，channels.lsp，F7 落地）

> 2026-09 更新：分块模式（`channels-blocks>=2`）**已降级为非默认**，原因见 N12 —— 不分块路径在交叉、穿盒、耗时三项上全面更优。以下分块机制说明保留，便于日后重估。

- 圆心按到点群外接矩形四边（上/下/左/右）的最近距离分到 4 个带。
- 每带沿带方向按 `字高+gap` 分列成网格（列数与圆心沿带方向顺序一致）；上/下带文字竖排（rot90, hj=1 vj=2），左/右带水平（rot0, hj=0/2 vj=2）。
- 每行在靠点群一侧留泳道区，泳道由 `dim-leader:ch-left-edge` 分配：同一泳道上的区间互不重叠，不同泳道 y/x 不同。
- 引线 = 圆心 →(深度) 泳道 →(沿带方向) 列 →(深度) 文字边，全正交。竖直/水平段只落在 圆心坐标 或 列坐标 上 → 引线零共线重叠。
- **列位（`u`）的放置是交叉数的决定因素**（N12）：PAVA 保序 + 最小行距，再整体平移使标签贴住**本行自己**的点范围。平移不破坏保序与最小行距，因此文字盒重叠恒为 0；贴住本行则避免引线纵穿全带去横切别行泳道。
- 残余代价：带越窄、点越密，堆的行数越多，深层行引线要越过外层泳道。本图竖臂 256 点挤在 46×176 里 → 6 行 → 779 处交叉。**根治要换思路**（见 N13），不是调参能解决的。
